Part 1

Project Foundation

1.1 Project Overview

CHAKRAVYUH is an AI-powered Red Team simulation platform designed to coordinate controlled cybersecurity experiments through a centralized AI Planner.

The platform allows a user to provide a security-testing objective. The AI Planner interprets the objective, selects an approved scenario, proposes structured execution parameters, and evaluates the results returned by the execution system.

The actual simulation work is performed by controlled Python adapters. The AI does not independently execute arbitrary operating-system commands.

The platform initially supports four simulation categories:

01
Authentication attack simulation

Synthetic Windows Event telemetry (4624, 4625, 4771) for SIEM testing without password theft.

02
Service-load simulation

Bounded Locust workload testing measuring RPS, error rates, and p95 latency on local endpoints.

03
Phishing-awareness simulation

Educational mock templates and synthetic mailboxes with zero credential harvesting.

04
Wireless-security simulation

Synthetic 802.11 beacon/deauth event records without physical radio transmission.

1.2 Project Objectives

  • Develop a centralized AI-based planning system.
  • Coordinate multiple Red Team simulation modules.
  • Implement deterministic execution and safety validation.
  • Support structured experiment configuration.
  • Collect and analyze simulation results.
  • Maintain an auditable execution history.
  • Provide a dashboard for experiment management.
  • Demonstrate the distinction between AI reasoning and conventional automation.

1.3 Project Scope

Included Scope
  • ✓ AI-assisted scenario selection
  • ✓ Structured simulation planning
  • ✓ Four controlled simulation modules
  • ✓ Target allowlisting & Parameter validation
  • ✓ Execution limits & Cooperative Emergency Stop
  • ✓ Result collection, observation feedback & SQLite history
  • ✓ Streamlit dashboard visualization
Excluded (Out of Scope)
  • ✕ Attacks against public or unauthorized systems
  • ✕ Unrestricted network flooding (DDoS)
  • ✕ Real credential theft & actual password harvesting
  • ✕ Unauthorized physical wireless disruption
  • ✕ Uncontrolled malware deployment
  • ✕ Autonomous execution of arbitrary OS commands

Centralized AI Planner

4.1 Why One Centralized Planner?

CHAKRAVYUH uses one centralized AI Planner rather than four independent AI agents. This guarantees consistent decision-making, centralized policy enforcement, shared experiment context, simpler testing, and uniform audit trails.

Part 5

Safety Gateway & Kill Switch

The Safety Gateway is the deterministic authorization boundary between AI planning and simulation execution. It must not rely on the AI model to decide whether an action is safe.

10-Point Sequential Gateway Verification

  1. Confirm request structure & Pydantic validation
  2. Confirm scenario category is enabled
  3. Confirm target identifier exists in database
  4. Confirm target is allowlisted for isolated subnet
  5. Validate parameter ranges against safety policy
  6. Check resource limits (memory/concurrency)
  7. Check execution rate limits
  8. Check experiment state validity
  9. Return deterministic approval or rejection
  10. Record decision immutably in SQLite audit log

from abc import ABC, abstractmethod

class BaseAdapter(ABC):
    @abstractmethod
    def validate_config(self, config: dict) -> bool:
        pass

    @abstractmethod
    def execute(self, request, cancellation_token) -> dict:
        pass

    @abstractmethod
    def get_status(self, run_id: str) -> dict:
        pass

    @abstractmethod
    def cancel(self, run_id: str):
        pass

    @abstractmethod
    def cleanup(self, run_id: str):
        pass

Part 18

Technical Reviewer Questions (Q1 to Q15)

Q1. Why use AI instead of fixed Python scripts? ▼

AI allows the system to interpret high-level testing objectives, select scenario profiles from catalogs, propose structured parameters, and analyze resulting telemetry. Python remains responsible for deterministic authorization, boundaries, and controlled execution.

Q2. Why use one AI Planner instead of four separate agents? ▼

A centralized planner prevents duplication, guarantees unified security policy enforcement, maintains single-session context across modules, simplifies automated testing, and produces clean, comparable audit records.

Q3. Can the AI directly execute commands? ▼

No. The AI produces structured JSON proposals. The deterministic Safety Gateway and Python execution engine independently validate and control what can run.

Q4. How do you prevent unauthorized execution? ▼

Through hardcoded target allowlists, scenario permissions, parameter validation bounds, resource limits, and adapter-level safeguards.

Q5. What happens if the AI generates invalid output? ▼

The Pydantic output validator rejects it immediately. It never reaches the execution layer.

Q6. What happens if the LLM provider is unavailable? ▼

The application reports a provider failure gracefully. A deterministic local fallback planner is used only if explicitly configured and clearly labeled as a fallback.

Q7 to Q10. Are the attacks genuine or synthetic? ▼

• Authentication: Generates synthetic logon telemetry (Event 4625) without real brute-force credential stuffing.

• Service-Load: Bounded workload against an authorized local test service; not a distributed flooding attack.

• Phishing: Harmless awareness drills with synthetic recipients; credential collection is disabled.

• Wireless: Generates synthetic 802.11 management frames; no physical radio frequency emissions.

Q11 to Q15. Monitoring, Auditing, SQLite, and Testing ▼

Execution state is tracked cooperatively. All prompts, validation results, gateway approvals/rejections, and observations are logged in SQLite. The system is verified through unit, integration, safety, and end-to-end tests.
